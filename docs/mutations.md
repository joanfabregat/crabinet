# Mutation and upload API

All routes below are under `/api/v1` and require an authenticated session with a grant for the share. Trash listing accepts a read grant; state-changing routes require effective `read-write` access and the authentication middleware's session-bound CSRF verification. Mounting the mutation router without that middleware fails closed with `403`.

Paths are canonical virtual paths relative to one configured share, at most 64 components deep. Absolute paths, paths with more components, dot segments, separators inside names, percent-encoded triplets, non-NFC Unicode, control characters, Windows device names, symbolic links, hard-linked files, and special files are rejected. Reserved internal names (`.crabinet`, legacy `.index-staging`, and the `.index-tmp-` prefix) are rejected in any ASCII letter case. A name that a request creates (a new file or directory, a move or rename destination with a different name, or a non-replacing upload filename) additionally rejects invisible or text-reordering characters: Unicode format characters (`Cf`, such as bidi overrides, zero-width spaces and joiners, and the byte-order mark) and line and paragraph separators (`Zl`, `Zp`). Existing entries with such names stay listed and usable, including moves that keep their name. A move never accepts another share identifier, so cross-share moves are impossible by construction.

## Routes

| Method and route | Body/query | Result |
| --- | --- | --- |
| `POST /shares/{share}/directories` | JSON `{ "path": "folder" }` | Creates one directory; an existing name is `409`. |
| `POST /shares/{share}/files` | JSON `{ "path": "file.txt" }` | Atomically publishes a new empty regular file; an existing name is `409`. |
| `PUT /shares/{share}/text?path=file.txt` | UTF-8 request body plus `If-Match` | Replaces a regular file if its metadata validator is current. |
| `POST /shares/{share}/move` | JSON `{ "source": "a", "destination": "b" }` plus `If-Match` | Renames a file or directory inside one share without replacing the destination. Moving a directory deeper is rejected with `400 path_too_deep`, before anything changes, if any entry would end more than 64 levels deep. |
| `DELETE /shares/{share}/entry?path=a` | `If-Match` | Moves a file or directory, including a nonempty directory, to the share's Trash and returns a `trashId`. A directory holding an entry more than 64 levels deep is refused with `400 path_too_deep` before anything changes, after the same bounded subtree walk a deeper move uses. |
| `GET /shares/{share}/trash?limit=100&cursor=` | None | Lists one page of published Trash items, newest first, for users with access to the share. `limit` is 1–200 (default 100); `nextCursor` is present when more items follow. Each page reads at most 100,000 Trash directory entries (about 50,000 items) and 8 KiB per sidecar, keeps only about twice the page size in memory, and shares the directory-listing limit of 16 concurrent scans, 8 per user; further requests receive `429` with code `busy`, and a Trash above the entry bound returns `413`. |
| `POST /shares/{share}/trash/{id}/restore` | JSON `{}` or `{ "destination": "other/path" }` | Restores without overwriting. An absent original parent, an occupied destination, or a location where an entry would end more than 64 levels deep (`400 path_too_deep`) leaves the item in Trash. |
| `DELETE /shares/{share}/trash/{id}` | None | Marks an item for permanent purge and starts bounded cleanup. |
| `POST /shares/{share}/trash/empty` | None | Permanently removes every item in the share's Trash, not just a listed page, and returns `{ "shareId", "outcome": "success", "purged", "failed", "moreRemaining" }`. See [Empty Trash](#empty-trash). |
| `POST /shares/{share}/uploads?path=folder` | `multipart/form-data`, file parts only | Streams files to the share's private staging directory and returns `207` with one outcome per file. |

The validator for replace, move, and move-to-Trash is the `ETag` returned by `GET /shares/{share}/metadata?path=...`. Missing, stale, or malformed `If-Match` values produce `409`. Uploads do not overwrite by default. With `replace=true`, each file part must carry its own `If-Match` header; a request-level header is accepted only as a fallback, which is mainly useful for a single-file request. Trash listing is available with read access; restore and purge require effective read-write access and CSRF verification.

## Integrity and resource behavior

Upload chunks are written directly to randomly named files under the writable share's private `.crabinet/staging` directory. The staging directory is created mode `0700`, opened without following links, reserved from the virtual path grammar, and omitted from listings and quota traversal. The server does not buffer a complete upload in memory. Text saves are buffered only up to `max_text_bytes` (1 MiB by default) so UTF-8 can be validated before publication. At most four text saves run concurrently across the process and two per user, admitted before the body is read, so a refused save buffers nothing and creates no staging file; further requests receive `429` with code `busy`. A text save whose complete body does not arrive within 60 seconds is aborted with `400` and the audit reason `body_timeout`. Text saves use their own limit rather than the upload slots, so editing a file is not refused while the browser runs its parallel uploads. Multipart requests are bounded by the configured payload limit plus a small capped framing allowance, file count, per-file bytes, aggregate file bytes, a process-wide concurrent-upload limit, a per-user limit of one less (at least one) so one user cannot hold every slot; the default allows four uploads in total and three per user, matching the browser client's three parallel uploads, and an optional share quota. An upload that delivers no new part or chunk for 60 seconds is aborted with `400` (audit reason `idle_timeout`), releasing its slot and every unpublished staging file. Because that idle timer restarts with every chunk, each upload request also has an absolute deadline for receiving its body: the configured upload size at 64 KiB/s, and never less than 10 minutes. With the default 256 MiB limit this is 4,096 seconds (about 68 minutes); at the 1 GiB ceiling it is 16,384 seconds (about 4.5 hours). Any complete upload that averages at least 64 KiB/s (about 0.5 Mbit/s) finishes, while a client trickling bytes cannot hold an upload slot indefinitely. An upload past its deadline is aborted the same way with `400` and the audit reason `upload_deadline`.

Filesystem work runs on the runtime's blocking thread pool, so a slow disk or network filesystem never stalls request handling. The lookup that a move or move-to-Trash performs before taking the share's commit lock counts against the shared blocking-work limit of 64 concurrent requests and 16 per user described in the [browse API](browse-api.md); further requests receive `429` with code `busy`. Quota checks and publication are serialized per share; mutations of unrelated shares do not wait for each other.

No destination is visible until its complete staged file has been flushed and synced. New files and moves use atomic no-replace renames. Replacements use an atomic exchange, revalidate both sides, and remove the old file only after validation. Staging and target-directory metadata are synced where the filesystem supports directory `fsync`; because the rename or unlink is already committed at that point, a directory `fsync` failure is logged and the mutation still reports success. A cancelled, malformed, oversized, or rejected request drops its capability-scoped staging-file guards and removes every unpublished file. Startup recovery performs one bounded, non-recursive pass over `.crabinet/staging` and removes only reserved `.index-tmp-<128-bit hex>` regular files without following links; it never traverses user content. A delete whose rollback fails leaves a retained `.index-del-` entry. A replacement renames its staged file to a retained `.index-rep-` name just before the exchange, so a replacement whose rollback fails keeps the previous file version there, and the error log names the entry. Startup recovery never deletes either kind of entry; it logs that they are kept for operator review.

Trash lives in private `.crabinet/trash`. Each item has an opaque-ID payload and a versioned JSON sidecar recording its original share-relative path, kind, deleting subject, deletion time, and expiration. Unknown sidecar schema versions fail closed. A pending sidecar is synced before the source is moved, then marked live after the move; startup reconciliation completes interrupted publications. Restore uses an atomic no-replace rename through validated share handles. Purge marks a sidecar before bounded, no-follow deletion, so startup and later GC passes can resume it. Trash content counts toward share quota. The default retention is 30 days, configurable with `server.trash_retention_days`. Collection starts with the server and runs hourly. Each run works through a share's Trash in batches of 1,000 directory names (about 500 items), taking the share's commit lock for one batch at a time, until it reaches the end of Trash or has spent 30 seconds on that share; the next run continues where it stopped. An item whose sidecar is unreadable, or whose payload cannot be removed (for example, one nested deeper than the 64-level depth limit), is logged by its opaque ID and skipped rather than stopping collection.

The Trash listing tolerates damaged and concurrently changing items. An item whose sidecar is corrupt, oversized, or from an unknown schema version, whose payload is missing or of a different kind than its sidecar records, or that a concurrent restore or purge removed while the listing ran, is left out of the response; a server warning names only its opaque Trash ID. Paging uses a keyset cursor: `nextCursor` carries the last item's deletion time and ID with an HMAC over the authenticated subject, share, and effective access, so a cursor cannot be forged, altered, or replayed by another user or after a grant change (`409`). Unlike a directory cursor, it does not fingerprint the listing: deletes, restores, and purges between pages never invalidate it, the next page simply starts after that position, and an item deleted meanwhile appears on the first page of a fresh listing.

## Empty Trash

`POST /shares/{share}/trash/empty` requires write access and a CSRF token, like every other mutation, and removes every published or already purging item in that share's Trash, including items on pages the client never loaded. It works in batches: each batch takes the share's commit lock, removes at most 1,000 items or payload entries, and releases the lock, so uploads and other writes to the share interleave with a large Empty Trash. Each batch reads the Trash directory from its start instead of resuming at a saved position, because some filesystems reorganize a directory, and invalidate saved positions, as entries are removed; removed items are gone, so every batch still makes progress. An item still being moved in is left alone. An item that cannot be read or removed, such as one nested deeper than the depth limit, is logged by its opaque ID, counted in `failed`, and passed over for the rest of the request, so it cannot stall the others.

A request stops when a complete read of Trash finds nothing left to remove, or after about 20 seconds of work, which keeps it well under common reverse-proxy timeouts. It then answers `200` with the number of items it removed (`purged`), the number it passed over (`failed`), and `moreRemaining: true` if it stopped for time; the client sends the request again to continue. Items deleted while it runs may or may not be included. Each request is audited as operation `empty_trash` with its counts, and refusals are audited with their reason like other mutations.

## Quota

With `max_share_bytes` set, creating a file or directory, saving text, and each uploaded file check the share's usage under its commit lock. Usage is the size of every regular file in the share and in Trash plus 4,096 bytes for every directory, including directories in Trash; a new directory is charged the same 4,096 bytes, and an over-quota directory creation returns `413`. Moves within a share, moves to Trash, and restores neither change usage nor check it. An upload request measures the share once and adds each published file's size to that figure under a single hold of the commit lock, instead of rescanning the share for every file.

A measurement visits at most 1,000,000 entries and descends at most 64 levels. A share it cannot measure is not reported as over quota: creation and saving return `507` with code `share_too_large_to_measure` or `share_too_deep_to_measure`, upload outcomes use the same two values, and the server logs the cause with the share ID and the bound. An operator must then reduce the share's entry count or flatten or remove the deep tree; other shares keep working.

Atomic rename requires staging and destination directories to be on the same filesystem. A writable share's staging directory is therefore inside its root. Writes into, and moves across, a nested mount on a different device are rejected with `400` and the stable `cross_device` audit reason rather than copied or published non-atomically.

A writable share must be owned by one Crabinet process or pod at a time. Multiple replicas pointing at the same writable directory are not supported because each process owns the private staging namespace and its recovery. Read-only shares create no staging directory and may use separate read-only replicas.

Multipart files are all staged before publication, so a parsing or request-limit failure publishes none of them. Publication is intentionally not a multi-file transaction: the `207` response reports `created`, `replaced`, `conflict`, `quota_exceeded`, `share_too_large_to_measure`, `share_too_deep_to_measure`, or `error` for each file. A later file failing does not roll back earlier successful files.

Successful and rejected mutations emit structured audit events containing the subject, share ID, operation, virtual path when appropriate, outcome, and stable reason. Every rejection inside a handler is audited, including invalid paths or names, stale or missing `If-Match` (`stale_validator`), missing entries, quota, busy upload, text-save, or blocking-work slots, idle or overdue uploads, timed-out text-save bodies, and cross-device writes. A malformed JSON body, query string, or multipart envelope is answered with the standard JSON error (`400 invalid_request`, or `413 too_large` for an oversized JSON body) and audited with that reason. Requests rejected before the handler runs (missing session or CSRF proof, or a share ID that is not valid UTF-8) are not audited here. File contents, credentials, host paths, session values, and CSRF tokens are never logged.

Replacement creates a new inode and does not preserve the prior file's timestamps, ownership overrides, extended attributes, or mode beyond the service process's configured umask. Operators should treat files with metadata requirements outside that model as read-only shares.
