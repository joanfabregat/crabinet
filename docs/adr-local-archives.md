# ADR: bounded local archive creation and extraction

Status: accepted.

## Context

Folder and selection downloads already produce ZIP streams. Users also need to create an archive inside a writable share and extract an existing archive there, without transferring its contents through the browser. Extraction adds an untrusted parser and a filesystem mutation boundary; compressed size alone cannot bound its memory, disk, inode, or CPU costs.

## Decision

Offer Compress on files, folders, and selections from one directory, and Extract on supported archive files. Both are authenticated, CSRF-protected write operations on one authorized share. Originals remain intact. Creation produces one new archive; extraction always produces one new folder. Atomic no-replace publication prevents merging with or overwriting existing files, directories, and links. Destination conflicts are errors, not automatic renaming. Neither operation recursively extracts archives found inside an archive.

Support ZIP (Store and DEFLATE, including ZIP64), TAR, TAR.GZ/TGZ, single-file GZ, and TAR.ZST for both creation and extraction. Unsupported ZIP codecs, encryption, split archives, self-extracting ZIP envelopes, TAR links, devices, FIFOs, sparse files, and global PAX extensions are rejected. Local PAX paths and sizes and GNU long names are read within a 16 KiB extension limit; PAX sizes must agree with the underlying header. Entry names must be UTF-8 and obey Crabinet's existing canonical and new-name policies. Standard leading `./` TAR prefixes and root directory markers are accepted; other dot segments are rejected. No ownership, permissions, executable bits, extended attributes, or link metadata are restored. Gzip's embedded filename is ignored; a standalone GZ produces a single file named after the source with its `.gz` suffix removed, inside the destination folder.

Use the existing pure-Rust `flate2` backend for DEFLATE and gzip. Add `zip` with default features disabled and only `deflate-flate2`, `tar` without default features, and `zstd` without default features. The locked graph adds eight packages, rather than an external archive executable or a second runtime service. Zstandard uses the maintained upstream native codec through its Rust bindings; its decoder window is capped at 8 MiB. ZIP's other codecs and encryption are not compiled in. Binary-size growth must be assessed from release artifacts rather than inferred from crate counts.

## Resource and publication invariants

- One gate admits two local archive operations process-wide and one per user. Its lease stays inside the blocking worker until work and cleanup finish, including after a request disconnects. A request waits at most five seconds for its share's commit lock; admission happens first, so pending workers are bounded too. The lock covers quota measurement, staging, and publication, preventing concurrent application writes from spending the same available quota.
- The existing download archive limits apply: by default 1 GiB of source/output bytes, 10,000 entries, and 4 MiB of relative names. Local operations never exceed 10,000 entries even if download walks allow more. Extraction counts implicit parent directories as created entries, checks actual emitted bytes as well as advertised sizes, and charges 4,096 quota bytes for every directory, including its destination root.
- The same `MAX_PATH_DEPTH = 64` as downloads applies to the complete destination path, not just the path inside the archive. Combined virtual path lengths also obey the existing grammar. Compression uses the download selection walk, including its no-follow entry checks, budgets, and exclusions.
- Parser input and decoded TAR streams have byte budgets, including metadata, padding, and empty compressed frames. TAR's decoded stream may contain at most the download byte cap plus 8 MiB of framing. ZIP's central directory is checked record by record before library parsing, capped at 8 MiB and the entry/name limits. The immutable snapshot prevents in-place source modifications from invalidating those checks. ZIP metadata discovery sees zero-filled file bodies, fixed archive offsets, and only the validated end records; embedded alternative end-record signatures in the metadata region are refused. This prevents fallback discovery from allocating an attacker-claimed ZIP64 extension before a read limit can intervene.
- Read/write buffers are at most 64 KiB, TAR extension buffers at most 16 KiB, gzip header strings are bounded by the existing codec, and Zstandard's window is at most 8 MiB. No whole payload or expanded tree is buffered in memory. Library metadata remains proportional to the bounded entry/name/directory sizes.
- Each worker has a 60-second cooperative deadline and checks cancellation between chunks and entries, including reads made by decoders. Work runs on the blocking pool. These bounds do not interrupt an operating-system call blocked on an unhealthy filesystem; the gate still bounds how many such workers can remain alive.
- Outputs remain in owner-only capability-scoped staging until complete. Extraction first snapshots the compressed input into a private file, then creates an unpublished directory tree. The snapshot and output together must fit the available configured share quota. Each file uses an exclusive no-follow open; all directory traversal uses no-follow directory handles. Libraries receive byte streams, never ambient output paths or permission to unpack into a host directory.
- Cancellation, validation failure, corruption, quota exhaustion, and destination conflicts remove unpublished files and trees. Tree cleanup and startup recovery use bounded no-follow removal and the same depth limit. Startup recovery shares one entry budget across staging names and tree contents; incomplete cleanup refuses recovery rather than traversing without a bound. Retained delete/replacement recovery entries remain untouched.

The browser displays an in-progress status and lets the user cancel. These are bounded request/response operations, without a persistent job registry, polling endpoint, or background queue. A disconnect near atomic publication can leave a complete result whose response the client did not receive; a refresh shows it, and retrying its destination receives a conflict. There is no promise of transactional cancellation after publication.

## Consequences and alternatives

Extraction temporarily needs disk space for both its compressed snapshot and its expanded output. Operators must provision share storage accordingly and use `max_share_bytes` where writers need a quota. As with uploads, repeated successful authorized writes can consume storage up to that quota; a per-request bound is not a lifetime storage quota. Unhealthy filesystems and bugs in third-party codecs remain residual availability risks, addressed by bounded admission, codec audits, adversarial tests, and process/container limits.

Reject delegating to shell tools: it would add executables to the minimal image and bypass capability-scoped output creation. Reject trusting library `extract`/`unpack` helpers: lexical path checks do not establish Crabinet's no-follow and new-name invariants. Reject eager TAR extension parsing and unchecked ZIP directory construction because attacker-controlled metadata can allocate memory before payload limits apply. Reject extraction into an existing directory because collisions, rollback, and link races would make partial failure substantially harder to reason about. Reject a persistent task system for this first version because the bounded operations need no durable queue. 7z, RAR, TAR.XZ, and TAR.BZ2 remain out of scope.

## Verification

Unit and route tests cover all supported round trips, canonical and hostile paths, links and special TAR entries, duplicate and conflicting paths, implicit-directory accounting, declared and actual expansion limits, oversized parser metadata, corruption, quota, cancellation/deadlines, no-replace publication, CSRF/write grants, and the 64-component destination boundary. The route inventory exercises the new gate process-wide and per subject. Browser tests create and extract each folder format using the production backend; dialog tests cover formats, naming, CSRF arguments, and cancellation races.
